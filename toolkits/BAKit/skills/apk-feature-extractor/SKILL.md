# APK Feature Extractor

Convert APK-decoder evidence into a structured **Feature Checklist** that matches the company's working template.

This skill is an **evidence extraction and normalization skill**.
It is not a research skill, not a product-decision skill, and not a technical estimation skill.

It answers:

> **The reference app has which feature groups, major features, sub-features, and what does each feature do?**

It does **not** answer:

> **Should our product implement the same feature? Is it feasible? How difficult is it? How long will it take? What priority should it have?**

Those decisions belong to Product/PO/Tech/Brainstorm or later planning stages.

---

## 1. Purpose

Use decoded APK documents to create or update the company's Feature Checklist.

The checklist is used as an intermediate BA artifact for:

- understanding the reference app feature set;
- selecting product scope;
- additional market/feature research;
- brainstorming and product decisions;
- Figma design planning/review;
- SRS writing;
- Dev/Tech feasibility and estimation.

The checklist is a **feature-scope artifact**, not a full SRS.

---

## 2. Expected Input

The skill accepts one or more Markdown files generated by an APK-decoder/competitor-analysis tool.

Typical inputs:

| Input | Primary purpose |
|---|---|
| `*_profile.md` | App overview, module map, high-level feature map, technical profile |
| `*_screens.md` | Screen inventory, purpose, entry points, UI components, actions |
| `*_flow-*.md` | User flows, interactions, system responses, observed rules, validations, state transitions |
| Other decoded `.md` files | Permissions, monetization, technical constraints, configuration, ads, purchase flows, etc. |

The skill must work even if only part of this set is available.

### Input completeness rule

1. Read all provided decoded documents.
2. Identify available evidence.
3. Extract only supported features and behavior.
4. Mark missing or unverified areas in notes when needed.
5. Never invent missing features or behavior.

---

## 3. Source Roles

### 3.1 `profile.md`

Use primarily for:

- module/feature-group discovery;
- high-level feature inventory;
- locating deeper evidence in screen/flow files.

### 3.2 `screens.md`

Use primarily for:

- screens/states;
- entry points;
- UI components;
- visible actions;
- navigation targets;
- visible feature states.

### 3.3 `flow-*.md`

Use primarily for:

- triggers;
- interaction sequences;
- system responses;
- state transitions;
- observed business rules;
- validations;
- edge conditions;
- success/error branches.

### 3.4 Technical/code evidence

Use to confirm or enrich feature understanding.

Technical details such as:

- Java/Kotlin class names;
- SharedPreferences keys;
- native SDK uniforms;
- codec internals;
- package/class paths;
- resource IDs;

must not dominate the feature description.

Only copy technical details into `Technology notes` when they are genuinely useful for later Dev/Tech discussion.

---

## 4. Evidence Types

Decoded documents may label information as:

- `[Observed]`
- `[Code]`
- `[Inferred]`

Preserve this distinction while extracting.

### Evidence priority

1. **Observed + Code aligned** → strongest evidence
2. **Observed only** → strong UI/behavior evidence
3. **Code only** → strong implementation evidence, but may not prove visible UX
4. **Inferred** → hypothesis only

### Critical rule

`[Inferred]` content must not be written as confirmed behavior unless another source supports it.

If a feature is only inferred, either:

- omit it from the main checklist, or
- include it with a clear note that it needs verification.

---

## 5. Company Feature Checklist Structure

The default checklist must use the following columns:

| Column | Purpose | Auto-fill rule |
|---|---|---|
| `STT` | Sequential number | Auto-fill |
| `Group of feature` | Feature group/module | Auto-fill |
| `Tính năng` | Major feature | Auto-fill |
| `Tính năng nhỏ` | Sub-feature | Auto-fill when applicable |
| `Mô tả tính năng` | Description of what the feature/sub-feature does and its important reference behavior | Auto-fill |
| `Link tham khảo` | Traceable source/evidence link or file reference | Auto-fill |
| `Khả thi` | Technical feasibility | Leave blank unless explicitly provided by Tech/Dev |
| `Mức độ` | Difficulty level, e.g. Dễ / Bình thường / Khó | Leave blank unless explicitly provided |
| `Thời gian (about)` | Estimated development time | Leave blank unless explicitly provided |
| `PO note` | Product Owner decision/note | Only fill from explicit PO input |
| `Ưu tiên` | Product priority | Leave blank unless explicitly provided |
| `Technology notes` | Technical notes/constraints useful for Dev/Tech | Fill only when evidence provides a meaningful technical constraint |

### Ownership rule

The extractor must **not** estimate or invent:

- feasibility;
- difficulty;
- development time;
- priority;
- PO decisions.

These fields remain empty until an authorized person or later workflow stage provides them.

---

## 6. Scope of Extraction

Extract user-facing or product-relevant capabilities such as:

- onboarding and app launch;
- home/navigation;
- core product features;
- content creation/editing tools;
- search/discovery;
- settings/preferences;
- account/authentication;
- subscription/IAP;
- ads/monetization placements;
- save/share/export;
- notifications;
- history/gallery/favorites;
- permissions when they affect product behavior;
- device-specific or hardware-gated behavior;
- important protection/recovery behavior.

### Do not create standalone checklist rows for

- every UI button;
- every Activity/Fragment/class;
- every SDK/library;
- implementation-only helpers;
- low-level constants;
- analytics events unless tracking itself is a feature;
- duplicate entry points to the same capability.

Example:

`Beauty` opened from Home and `Beauty` opened inside Camera are normally the same feature, not two separate features.

---

## 7. Feature Granularity Rules

The checklist should reflect the hierarchy visible in the company's template:

> **Group of feature → Tính năng → Tính năng nhỏ**

### Example hierarchy

- Group of feature: `Camera`
  - Tính năng: `Beauty`
    - Tính năng nhỏ: `Skin Beauty`
    - Tính năng nhỏ: `Facial Retouch`
    - Tính năng nhỏ: `Makeup`

### Good granularity

- Image Collage → Layout / Background / Frame
- Camera → Aspect Ratio / Beauty / Filters / Video
- Edit Image → Crop / Mosaic / Adjust / Text / Stickers

### Too broad

- Camera
- Editor
- Settings

These are normally feature groups, not a single feature row.

### Too granular

- individual button IDs;
- each slider value;
- each code constant;
- each color/style token.

### Parameter rule

Do not explode parameters into separate rows unless they represent meaningful independent sub-features.

For example, `Smooth`, `Whiten`, `Teeth` should normally stay inside the description of `Skin Beauty`, not become separate checklist rows.

---

## 8. Duplicate & Merge Rules

The same feature may appear in profile, screen, and flow documents.

Before creating a new row:

1. compare feature purpose;
2. compare target module/screen;
3. compare user behavior;
4. merge evidence if they describe the same capability.

Do not create duplicates merely because:

- the feature has multiple entry points;
- the same feature appears in several decoded files;
- multiple classes implement one feature.

If a feature has multiple entry points, mention that briefly in `Mô tả tính năng` only if it is useful, otherwise keep it in the evidence link/source.

---

## 9. `Mô tả tính năng` Rule

`Mô tả tính năng` replaces the old `Basic Description` + `Reference Behavior Summary` concept.

It should answer:

1. What does the feature/sub-feature allow the user or system to do?
2. What is the main functional purpose?
3. What important reference behavior should be carried forward for Product/BA understanding?

### Include

- capability;
- main behavior;
- key options;
- meaningful limits/gates;
- important persistent behavior;
- important reference branching when relevant.

### Do not include

- full use case;
- every validation/error case;
- full code implementation;
- speculative recommendation;
- target-product decisions not yet approved.

### Example

Good:

> Cho phép người dùng thay đổi tỷ lệ khung hình trước khi chụp. App reference hỗ trợ 1:1, 4:3, 16:9 và Full; lựa chọn hiện tại được lưu lại cho lần sử dụng sau.

Too technical:

> Tap `camera_resize`; `PopupCameraResize` đọc SharedPreferences `resize1`, map 0/1/2/3 và ẩn Full khi tỷ lệ màn hình <= 1.778.

The detailed technical rule stays in APK Evidence and may later be used when writing SRS.

---

## 10. `Link tham khảo` Rule

Every extracted feature/sub-feature must be traceable to evidence.

Preferred sources:

1. exact decoded file/section;
2. screenshot path if available;
3. flow document;
4. screen inventory;
5. profile feature map.

If the output format supports clickable links, use them.
If not, use a clear source reference such as:

- `flow-camera.md > Aspect Ratio`
- `screens.md > Camera Viewfinder`
- `profile.md > CF-007`

When several sources support the same row, include the most useful 1–3 references, not every duplicate occurrence.

---

## 11. `Technology notes` Rule

`Technology notes` is optional and should stay concise.

Use it only for technical facts that may materially affect implementation or design discussion, for example:

- feature disabled on low-RAM devices;
- specific OS/API dependency;
- feature requires camera/location/storage permission;
- online assets/CDN dependency;
- special hardware requirement;
- third-party SDK dependency;
- meaningful performance/codec constraint.

Do not fill it with:

- obfuscated class names;
- every SDK/library;
- implementation trivia;
- low-level constants that are irrelevant to planning.

Example:

> Hand-tracking feature is disabled on low-RAM devices in the reference app.

Not recommended:

> Implemented in `AbstractC10835b.java:55-59` using `f22799c = 2`.

---

## 12. Product Decision Boundary

This skill describes the **reference app**, not the target product.

It must not decide:

- Keep;
- Modify;
- Remove;
- New;
- target parameter values;
- target navigation;
- target business rules;
- target priority.

If the user/PO has already provided a product decision, it may be copied into `PO note` exactly as given.

Do not silently transform reference behavior into target requirement.

---

## 13. Conflict Handling

When decoded documents conflict:

1. do not silently reconcile;
2. keep the feature in the checklist if its existence is clear;
3. describe only the common confirmed behavior in `Mô tả tính năng`;
4. add a short conflict note in `Technology notes` or `PO note` only if needed;
5. keep evidence links to both conflicting sources;
6. do not choose a target behavior.

Example:

> `screens.md` reports 6 categories while `flow-camera.md` reports 10 categories.

Checklist description:

> Cho phép người dùng chọn preset theo nhiều nhóm category.

Technology notes:

> Reference evidence is inconsistent on the exact category count; verify before reuse.

---

## 14. Extraction Process

### Phase 1 — Inventory Inputs

1. List all provided decoded files.
2. Identify app/package/version if available.
3. Identify evidence coverage:
   - profile;
   - screen inventory;
   - flows;
   - technical docs;
   - blocked/unvisited areas.

### Phase 2 — Build Candidate Feature Set

Start from:

1. profile feature map if available;
2. screen-level capabilities;
3. flow-level capabilities missing from profile;
4. monetization/settings/supporting capabilities.

### Phase 3 — Normalize Hierarchy

For each candidate:

- assign `Group of feature`;
- determine `Tính năng`;
- determine `Tính năng nhỏ` where applicable;
- merge duplicate evidence;
- remove implementation-only items.

### Phase 4 — Write Feature Description

For each row:

- describe the feature purpose;
- include important reference behavior;
- include key options/limits only when useful;
- keep detailed logic in APK Evidence.

### Phase 5 — Add Evidence & Technical Notes

- fill `Link tham khảo`;
- add meaningful technical constraints to `Technology notes`;
- leave planning/estimation columns blank.

### Phase 6 — Coverage Check

Check that:

- every major module has corresponding features;
- important user-facing flows are represented;
- monetization/settings/support features are not missed;
- duplicate entry points are merged;
- unvisited branches are not stated as confirmed behavior.

### Phase 7 — Output

Produce:

1. Source Summary;
2. Feature Checklist;
3. Coverage / Verification Notes if needed.

## 16. Existing Checklist Update Mode

If a checklist already exists:

1. preserve existing `STT`, grouping, and naming where possible;
2. match APK-extracted features to existing rows;
3. enrich `Mô tả tính năng` and `Link tham khảo` from APK evidence;
4. add newly discovered reference features as new rows;
5. never overwrite explicit PO notes, feasibility, difficulty, estimate, or priority;
6. never delete target-only features just because they are absent from the APK reference.

If a checklist item is not found in current APK evidence, add a note only when helpful:

> `Not found in current APK evidence; may be a target-only/new feature.`

---

## 17. Boundaries

This skill MUST NOT:

- browse the web for additional research unless explicitly requested by the caller;
- redesign the target product;
- recommend which competitor features to copy;
- assign feasibility/difficulty/time/priority without explicit input;
- create final target business rules;
- generate full SRS/use cases;
- infer missing UX as fact;
- treat decoded source as the target product specification.

This skill MAY:

- consolidate duplicate evidence;
- identify contradictions;
- flag missing coverage;
- summarize important reference behavior inside `Mô tả tính năng`;
- capture meaningful technical constraints in `Technology notes`;
- prepare traceable input for Research, Brainstorm, Business Analyst, and SRS stages.

---

## 18. Handoff to Next Stage

After extraction, the Feature Checklist becomes an input artifact for later stages.

Recommended routing:

- Need additional market/feature knowledge → `ba-researcher`
- Need product choice or unresolved behavior → `ba-brainstormer` / `brainstorm-features`
- Target decisions and Figma are ready → `ba-spec-writer` / `specs`
- Need feasibility/difficulty/time estimation → Dev/Tech review

Do not automatically invoke the next stage unless the workflow or user explicitly requests it.

---

## 19. Critical Rules Summary

1. **APK Evidence describes the reference app, not the target product.**
2. **Feature Checklist defines feature scope, not full requirements.**
3. **Use the company's exact checklist columns.**
4. **`Mô tả tính năng` includes both basic purpose and important reference behavior.**
5. **Do not create a separate `Reference Behavior Summary` column.**
6. **Do not auto-fill Khả thi / Mức độ / Thời gian / Ưu tiên.**
7. **Only fill PO note from explicit PO input.**
8. **Only fill Technology notes with meaningful technical constraints.**
9. **Never convert `[Inferred]` content into confirmed facts.**
10. **Merge duplicate features across profile/screens/flows.**
11. **Never silently resolve conflicting evidence.**
12. **Do not research outside the provided APK evidence in this skill.**
13. **Do not write SRS or implementation instructions here.**
14. **Maintain traceability from every extracted feature back to evidence.**
